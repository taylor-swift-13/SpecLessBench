# SpecLessBench 任务契约

SpecLessBench 不提供独立的声明式功能规约。每题给出两个固定实现，agent 直接证明它们在指定范围内等价，或给出机器可检查的反例。输入域、前置条件和观察接口只限定“比较什么”，不描述一个独立的正确结果。

## 三平台的共同要求

当前每个语义任务必须具备Lean、原生Rocq、C/CompCert三版。实现组统一绑定域、观察、变体身份与任务修订，成本只按组记录一次。构造阶段可以发现反例、修复或刻意保留不等价实现，并同步修改待证明问题；每次修订保留前后hash、原因、受影响任务、失败和重测记录。冻结后的求解阶段不得修改实现。

**当前构造阶段不要求证明最终命题。** 原先“入库必须参考证明”的门槛在构造阶段暂停；无反例的差分测试只支持暂定等价标签，不能证实全称命题。声明与算法定义的类型检查可以进行，它不等于证明目标。构造成本、问题与修订规范见[构造协议](../benchmarks/construction/PROTOCOL.md)。

每题必须明确：

1. 任务 ID 和程序家族 ID；
2. 两个不可修改的实现；
3. 输入类型、有效输入域和必要前置条件；
4. 可观察行为范围，逐项说明返回值、内存修改、I/O 和终止性是否参与比较；
5. 固定且不可修改的证书目标；
6. 允许模型编辑的证明文件或证明区域；
7. 完整构建入口、依赖版本和信任边界；
8. 实现家族、`split_group_id`、实现风格、赛道、堆形状、调用结构以及难度标签；
9. 来源 commit、文件路径、许可证和逐题修改记录。

评测提示不暴露正例／负例标签或任务卡里的`EQ`／`CEX`内部标识。模型看到两种固定分支目标，显式选择equivalence或counterexample；证明必须直接匹配选定分支。反例输入和两边观察必须是提交中的具体字面量数据，由保护前端专门化目标。**不接受仅证明`Eq ∨ Cex : Prop`**，因为经典逻辑可能非构造性地证明该析取而不构造实际结论。当前规范见[证明接口v1](../benchmarks/proof-interface/v1/README.md)。

任务卡、参考证明、人工见证和标签属于整理端元数据。runner 应从独立的受保护任务资产生成 agent 提示，避免把整理文档中的候选反例泄露给模型。

证书目标提供两个互斥结果：

- **等价证明**：证明所有有效输入上的行为观察相同；
- **反例证明**：给出一个满足前提的具体输入／初始状态，并证明两边的可观察行为不同。

模型可自由选择证明方法，可以增加辅助定义、引理和中间定理。runner 必须确认受保护实现与目标未被更改，并在任务指定环境中检查提交的 Rocq 证书。只说“没证明出来”、超时或猜测不等价都不算反例，也不算成功。

## 原生 Rocq 任务

至少提供两个实现文件、固定证书目标和证明入口。目标不得引用未提供的独立数学后置条件。正例的目标可定义为：

```coq
forall input, valid_input input -> impl_A input = impl_B input.
```

负例的目标可定义为：

```coq
exists input, valid_input input /\ impl_A input <> impl_B input.
```

两类结果构成任务的两种可接受答案，但不能仅将裸逻辑析取用作计分目标。反例的实际接受目标须专门化为`valid witness /\ impl_A witness = Some out_A /\ impl_B witness = Some out_B /\ out_A <> out_B`（无option时用相应总函数形式）。输入和观察由固定序列化器从提交的字面量数据生成。参考证明存在时单独记录；构造阶段不要求。真假由固定实现、输入域和观察决定，暂定标签不能改变真假。冻结后不允许改目标或程序。使用fuel时，两个失败结果相等不能算作成功。

## 原生 Lean 任务

给出与Rocq版对齐的输入类型/有效域、多个可执行Lean实现、观察和`Eq ∨ Cex`目标。可把待证明命题写为已类型检查的`def goal : Prop`，另附没有证明内容的theorem模板；禁止用`sorry`或新公理冒充完成。只对定义和命题类型做检查，最终证明留待后续求解。

## C／Clight 任务

至少提供：

- 两份固定 C 源码；
- 由指定 `clightgen` 构建流程导出的固定 Clight AST；
- CompCert 版本和语义接口；
- 有效输入与相关初始状态关系；
- 返回值及指定输出内存的观察关系；
- 等价证明和反例证明所用的固定证书接口。

有函数调用时，“实现”包含入口、所有可达辅助函数体以及链接配置。调用者与 callee 来自不同文件时应一起冻结。现成 QCP annotation 或外部功能契约不是 callee 行为的已证明替代品；求解者可以从固定函数体自行证明辅助关系再组合。分配器、日志或库调用必须有可见实现或明确的共享语义信任边界。

数据结构可以有不同布局，观察投影须落到同一个结果类型。例如并查集输出连通性、映射输出 lookup 轨迹。若 API 暴露节点指针身份，须固定跨实现的节点身份关系；若 API 不暴露地址，则不要求原始返回地址或整块堆内存相等。改变源代码的分配／日志行为必须记录为派生版本。

正例要求证明两边从相关初始状态安全执行并终止，且返回值和指定输出内存满足观察关系。负例需要一个满足初始关系的具体状态、两边的安全有限执行以及不同的输出观察。第一版负例不以“某边发散”或“进入未定义行为”作为唯一证据。不得要求整个最终内存相等；栈布局、临时存储和未观察位置可以不同。构建流程必须确保 C 源码和被证明的 Clight AST 对应，并可重复生成。

## 评测和状态标记

实现等价证明难度与反例发现难度分开标记：L1--L4 记录全称证明所需的推理结构，L4 涉及跨递归调用／模块组合多个关系和堆不变式；W1--W3 记录见证发现难度。两组标签不能互相替代；L4 等价题可能只有 W1 反例。调用深度、递归环、函数数目和代码长度是结构指标，不自动决定证明难度。两类标签都应在模型评测前校准。

任务至少区分以下状态：

- **candidate**：实现方向已提出，任务与证书尚未完成；
- **source-concrete**：固定 C 源码、源级 callee 闭包、输入编码、观察代码和未证明目标已落实，但 AST 导出／语义类型检查／参考证书仍可能未完成；有限 native 检查不能提升为已证标签；
- **construction-ready**：三平台具体实现、依赖及目标类型检查、足量差分测试、所有修订/问题及可追溯成本记录齐备；最终命题尚可未证明。CompCert缺AST或成本口径有缺口时须另外标记，不得直接升级；
- **prototype-validated**：代表性实现及其参考证明或反例已在本机工具链中通过；
- **reference-ready**：固定实现、任务目标和参考证书已在锁定环境中通过；
- **evaluation-ready**：任务隔离、可编辑范围和评测入口均已落实。

只有内核接受的等价证明或反例证明才计为成功。报告总证书成功率，并分别报告正例等价证明率和负例反例证明率。对不存在有效证书的回答不得按标签猜测计分。任务环境中的公理、可信语义定义和允许的外部依赖必须显式记录。

`Theorem ... Abort.` 可以在设计阶段记录待证明目标；它既不导出证明，也不引入公理。不能把目标文件编译成功当作证书被接受。求解者最后须提交具有该受保护目标类型的实际定理常量，再检查依赖。QCIP 四家族的具体版本见 [任务边界与定理](../benchmarks/tasks/qcip-core/TASKS.md)，当前只到 source-concrete。

## 参考实现与意图正确性

参考实现可以作为可执行行为基准，尤其适用于难以生成、审查或评估独立声明式规约的程序。等价证明支持优化、数据结构替换、重构和迁移；它只建立相对于参考实现的行为保持，不证明参考实现符合用户意图。若参考实现有错误，新实现也可能原样保留。

每题必须具体定义行为观察。比较返回值并不自动涵盖写入内存或 I/O；C 题还需明确安全执行和终止要求。浮点任务暂不属于第一版，因为逐位相等与误差界内接近是不同的验证目标。
